# CLAUDE.md

Guidance for Claude when working in this repository.

## Project Overview

- This is a fork of Bespoke OLAP (original repo: an LLM-driven C++ OLAP-engine synthesis pipeline).
- Phases 1 and 2 establish the foundation: dev container, TPC-H data, validation harness, and a minimal static build of the host process.
- Phase 3 is the real work: synthesizing a bespoke C++ engine under `output/` using Claude.
- First synthesis target: **TPC-H Q1** (single-table aggregation over `lineitem`).

## Architecture

- `template/` — C++ engine skeleton. `db.cpp` is the host process; loader / builder / query are split into `*_api.{hpp,cpp}` + `*_impl.{hpp,cpp}` pairs that are designed to be compiled into separate `.so` plugins and dlopen'd at runtime by the host. `utils/` is header-only IPC + plugin machinery plus a tiny `build_id.cpp`.
- `data/` — TPC-H Parquet files (generated by `scripts/gen_tpch.sh`).
- `reference/` — reference SQL (currently just `q1.sql`); the source of truth for query semantics.
- `docs/expert_knowledge.md` — DB optimization knowledge base; consult during the optimization phase.
- `docs/PHASE1.md`, `docs/PHASE2.md` — per-phase status notes.
- `output/` — destination for synthesized bespoke engines (created in Phase 3).
- `_legacy/` — the original OpenAI-based orchestrator. Reference only; do not modify.

## Build & Test

- C++ build: `make -C template` produces `template/build/db`.
- Smoke run: `./template/build/db` (no args) prints usage and exits 1. This is the expected Phase 2 behavior; running with a parquet dir requires the Phase 3 plugin `.so` files plus the `P2C_FD` / `C2P_FD` env vars set by `template/compiler.py`.
- Result validation: `python3 validate.py --engine <exec> --query <q_id> --data-dir data/`. Compares engine stdout (CSV) against DuckDB.
- Data generation: `bash scripts/gen_tpch.sh [scale_factor]` (default SF=1).

## Critical Constraints

- **C++20 is required.** Apache Arrow 24.x headers use `std::span`, `std::bit_width`, `std::popcount`. Every compile command must pass `-std=c++20` (the Makefile does this).
- Container runs on **aarch64 (ARM)**. Do not introduce x86-only intrinsics; if porting code that uses SSE/AVX, replace with portable equivalents.
- **Single-threaded is acceptable** (matches the original paper's scope).
- **In-memory engine only.** Disk-resident storage is out of scope.
- **Correctness gate:** every query result must match DuckDB exactly. Verify with `validate.py` after each implementation step.

## Synthesis Workflow (Phase 3)

When synthesizing a bespoke engine under `output/`, work in three stages and `git commit` after each:

1. **Storage plan** — inspect `data/` samples and the query SQL, decide the in-memory physical layout. Output: `output/storage_plan.md`.
2. **Base implementation** — write loader / builder / query in C++ following the storage plan. Optimize for correctness only; do not chase performance yet. Validate with `validate.py` before committing.
3. **Optimization** — instrument with tracing, consult `docs/expert_knowledge.md`, iterate. Re-validate after every change.

If a step regresses (fails validation or measurably slower), `git reset --hard` back to the previous commit and try again.

## Tools Allowed

- Claude tools: `Bash`, `Edit`, `Read`, `Glob`, `Grep`, `Write`.
- Standard CLIs: `make`, `g++`, `clang++`, `duckdb`, `python3`, `git`.
- Off-limits:
  - `_legacy/` — read only, never modify.
  - `template/compiler.py` and `template/compiler_cached.py` — read only in Phase 2; Phase 3 will re-enable them.
